# Answers — Homework 2: Git and GitHub

## 1. What is the difference between a working directory, the staging area, a commit, and a remote repository?

The working directory contains the files I am currently editing. The staging area contains the changes I have selected for the next commit. A commit is a saved snapshot of the staged changes, with a message and a place in the repository's history. A remote repository is a version of the repository hosted elsewhere, such as on GitHub, which I can push to and pull from.

## 2. What do `HEAD`, `main`, and `origin` refer to in a normal repository?

`HEAD` identifies the commit or branch currently checked out in my local repository. `main` is the name of the main branch, which is commonly used as the primary line of development. `origin` is the conventional name Git gives to the remote repository from which the local repository was cloned.

## 3. Why should you pull or fetch recent `main` changes before starting new work?

I should update my view of `main` before starting so I do not build on an outdated version of the project. This helps me see teammates' latest changes, reduces avoidable integration conflicts, and makes it easier to detect problems early.

## 4. What is the difference between fetching and pulling?

`git fetch` downloads new commits and updates remote-tracking references, but it does not integrate those changes into my current branch. `git pull` fetches the changes and then integrates them into the current branch, usually by merging or rebasing depending on the configuration and options.

## 5. What is the difference between merging and rebasing? When is rebasing a shared branch dangerous?

Merging integrates changes from another branch and can create a merge commit that records both histories. Rebasing replays my commits on top of a different base commit, creating new commit IDs and making the history more linear. Rebasing a shared branch is dangerous when other people have based work on its existing commits, because rewriting those commits can make their histories diverge and force collaborators to repair or rebase their work.

## 6. Why are pull requests useful even though they are not part of Git itself?

A pull request is a feature provided by hosting platforms such as GitHub, rather than by Git itself. It gives a team a place to review changes, discuss the implementation, run automated checks, and decide whether to merge a branch into the target branch. This can catch errors before they reach the main branch.

## 7. In Task 4, Git created a new commit called `Merge branch 'can'`. Why was a new commit needed?

`main` and `can` had each received commits after they diverged from their common starting point. A fast-forward was therefore not enough to bring the branches together. The merge commit records the integration and has both branch histories as parents, preserving the fact that the two lines of development were joined.

## 8. In Task 5, both branches changed `src/main.cpp`. Why did `can_id` merge by itself but `@version` and `loop()` did not?

The `can_id` line was changed only on `main`, so Git could apply that change without choosing between competing edits. The `@version` line and `loop()` contained overlapping changes on both branches, so Git could not determine which version was intended. Those conflicts had to be resolved manually in the Merge Editor, choosing the incoming version for `@version` and the current `slow-blink` version of `loop()` with `delay(500)`.

## 9. In Task 6, which workflow ran when you pushed to `ci`, and which did not? Why? What does the CI workflow protect the team from?

The `PlatformIO CI` workflow ran when I pushed to `ci`, compiling the firmware to check that the code builds. The `Doxygen GitHub Pages Deploy Action` did not run because it is configured to run on pushes to `main`, not on the `ci` branch. The CI workflow helps protect the team from merging code that fails to compile.

## 10. What does a `.gitignore` file do, and why does it not remove a file that was already committed? Why is `.pio` in `.gitignore`?

A `.gitignore` file tells Git which untracked files or directories it should normally leave out of version control. It does not remove a file that is already tracked, because Git continues tracking that file until it is explicitly removed from the index or the repository. `.pio` is generated by PlatformIO and can contain local build artifacts and downloaded build data, so it usually should not be committed.
